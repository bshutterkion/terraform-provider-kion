# Terraform Provider for Kion

A Terraform provider for the [Kion](https://kion.io) cloud governance platform, built on the [Terraform Plugin Framework](https://developer.hashicorp.com/terraform/plugin/framework) and structured after the [HashiCorp AWS provider](https://github.com/hashicorp/terraform-provider-aws).

## Overview

Generated from the Kion OpenAPI specification, this provider manages 72 service packages covering organizational management, cloud access, compliance, financial governance, and more. Almost everything is generated: resource CRUD, schemas, data sources, acceptance-test scaffolding, `.tf` examples, registry docs, and a Terraform module per resource.

The provider is built against a **single** Kion API version — the SDK's `generated/v3_16` sub-package. It does not ship a separate release line per Kion version. Compatibility with older self-hosted instances is handled at runtime instead: `codegen/version_support.yaml` records the Kion version range in which each resource's defining API operation exists, and resources whose operation is not present in every supported version carry a generated version gate that fails with a clear diagnostic when pointed at an instance too old to support it.

## Provider Configuration

```hcl
terraform {
  required_providers {
    kion = {
      source = "registry.terraform.io/kionsoftware/kion"
    }
  }
}

provider "kion" {
  api_url = "https://your-kion-instance.com"  # or KION_API_URL
  api_key = var.kion_api_key                  # or KION_API_KEY
}
```

An app API key is all you need. `api_key` is sent as `Authorization: Bearer <value>`.

<details>
<summary>Other accepted attributes</summary>

| Attribute | Notes |
|---|---|
| `auth_token` / `KION_AUTH_TOKEN` | Accepted, but not a distinct credential type — it is sent as the same `Authorization: Bearer <value>` header as `api_key`, and `api_key` wins if both are set. Prefer `api_key`. |
| `skip_ssl_validation` / `KION_SKIP_SSL_VALIDATION` | Skip TLS verification. |
| `url`, `apikey` | Deprecated aliases carried over from the previous provider. Use `api_url` and `api_key`. |
| `apipath` | Base path appended to `api_url`, defaulting to `/api` — same meaning as in the previous provider, including `apipath = ""` to address an API mounted at the root. Rarely needed. |

Configuration fails if neither `api_key` nor `auth_token` is supplied, and if `api_url` is missing.
</details>

## Architecture

### Service Package Pattern

The provider follows the [AWS provider's service-package architecture](https://hashicorp.github.io/terraform-provider-aws/service-package-layout/). Each Kion resource lives in its own package under `internal/service/<name>/`:

```
internal/service/label/
  label.go                     # Resource CRUD (generated by kgen crud)
  label_schema_gen.go          # Schema + model (generated from the OpenAPI spec)
  label_data_source.go         # Data source
  label_version_gen.go         # Kion version gate, when the resource needs one
  label_test.go                # Acceptance tests
  service_package.go           # Factory registration
```

Resources embed `framework.ResourceWithConfigure` (data sources embed `framework.DataSourceWithConfigure`), which inject the shared `KionClient` from the provider's `Configure` method.

**Generated files carry a `// Code generated by kgen …  DO NOT EDIT.` header — edit the codegen inputs, not the output.** See [Code Generation](#code-generation).

### Directory Structure

```
.
├── cmd/
│   ├── kgen/                   # Code generator CLI (schemas, crud, modules, examples, tests)
│   ├── kconfig/                # Derives codegen/generator_config.yaml from the service packages
│   ├── kalign/                 # Schema/SDK alignment checks
│   └── kversions/              # Derives codegen/version_support.yaml from the SDK
├── codegen/                    # Hand-maintained generator inputs (see Code Generation)
├── internal/
│   ├── acctest/                # Acceptance test helpers
│   ├── conns/                  # KionClient wrapper, raw HTTP for endpoints the SDK lacks
│   ├── errs/                   # SDK response -> diagnostics helpers
│   ├── flex/                   # Type converters: TF <-> SDK
│   ├── framework/              # Base types, Kion version gates
│   ├── kgen/                   # Generator implementation and templates
│   ├── provider/               # Provider definition and registration
│   ├── provider_kion/          # Generated provider schema (from tfplugingen)
│   ├── service/                # 72 service packages (one per resource)
│   └── servicepkg/             # Shared registration types
├── spec/                       # gitignored: local codegen input, fetched by make refresh-spec
├── modules/                    # 72 generated Terraform modules (one per resource)
├── examples/                   # Generated .tf examples (resources, data sources, provider)
├── docs/                       # Registry documentation (tfplugindocs)
├── .gitlab-ci.yml              # GitLab CI pipeline
├── .github/workflows/          # GitHub Actions (release only; GitLab CI is primary)
├── .golangci.yml               # Linter config (aligned with terraform-provider-aws)
├── lefthook.yml                # Pre-push git hooks
└── Makefile                    # build, test, lint, CI, install, codegen
```

### SDK Integration

The provider uses [kion-sdk-go](https://github.com/bshutterkion/kion-sdk-go) — a typed Go SDK generated from the Kion OpenAPI spec with [ogen](https://ogen.dev/). Resource code imports the `generated/v3_16` sub-package, aliased `generated`.

Type conversion between Terraform Framework types (`types.String`, `types.Int64`, …) and SDK types (`generated.OptString`, `generated.OptUint64`, …) lives in `internal/flex`.

The SDK is referenced through a `replace` directive in `go.mod` pointing at `../kion-sdk-go`, the **published Go mirror** of the SDK.

**`spec/openapi3.json` is not committed** — it is gitignored. This repo is published for customers and ships the provider, not Kion's interface files. Because the generated code *is* committed, a plain clone still builds, tests, and regenerates modules, docs, and examples with no spec present.

Only the two schema generators read it (`make generate-schemas`, `make config-gen`), and `make refresh-spec` fetches a local copy from the SDK spec source (maintainers only; set `SDK_SPEC`). Override `SDK_SPEC=<path>` if your checkout differs. `SDK_VERSION` in the Makefile (`v3_16`) is the Kion version the provider targets and selects both the spec and the `generated/<v>` sub-package the code imports.

A few endpoints the public spec does not expose are served over raw HTTP through `internal/conns`; those are declared in `codegen/private_endpoints.yaml`.

## Code Generation

Nearly the whole provider is generated. The inputs live in `codegen/` and are the files to edit:

| File | Purpose |
|---|---|
| `generator_config.yaml` | Per-resource CRUD paths driving schema generation (derived; see `config_overrides.yaml`) |
| `config_overrides.yaml` | Hand-tuned paths `kconfig gen` cannot derive |
| `schema_overrides.yaml` | What the spec cannot express: descriptions, plan modifiers, type changes, attribute removal |
| `crud_archetypes.yaml` | Which CRUD shape each resource uses (entity, blended, association, parent_list, …) |
| `private_endpoints.yaml` | Endpoints absent from the public spec, plus their read shapes |
| `renames.yaml` | Attribute renames |
| `version_support.yaml` | Kion version ranges per resource (derived by `kversions`) |
| `test_values.yaml` | Sample values for generated acceptance tests |

```bash
make refresh-spec             # Fetch the OpenAPI spec locally (needs the kion-sdk monorepo)
make generate                 # version gates + schemas + CRUD
make modules                  # Terraform modules + terraform-docs injection
make examples                 # .tf examples
make docs                     # Registry docs (tfplugindocs)
```

`make crud` and the other generators **skip files that already exist** — pass `--force` to regenerate:

```bash
go run ./cmd/kgen crud --force                    # all resources
go run ./cmd/kgen crud --resource label --force   # one resource
```

Scaffolding a brand-new service package:

```bash
go run ./cmd/kgen service --name CloudRule --snakename cloud_rule
```

Then add its entries to `codegen/` (paths, archetype, and a read shape if the read is private) and regenerate.

> Adding or removing a resource changes four generated surfaces — `internal/service/`, `examples/`, `docs/`, and `modules/` — and only `modules/` has a CI drift gate. Regenerate all four. It also changes the supported surface tracked by the sibling `terraform-coverage-test` project; run `make coverage-new` there and add modules for anything newly reported as a gap.

## Development

### Prerequisites

- [Go 1.25+](https://go.dev/doc/install)
- [golangci-lint v2](https://golangci-lint.run/welcome/install/)
- [lefthook](https://github.com/evilmartians/lefthook) (git hooks)
- The SDK is resolved from the module proxy — no sibling checkout needed. Regenerating schemas additionally needs a local SDK spec (`SDK_SPEC`))
- `make install-codegen-tools` — pinned tfplugingen-openapi, tfplugingen-framework, tfplugindocs
- Terraform 1.14.8 and `terraform-docs`, for the module tests

### Common Commands

```bash
make build                    # Build provider binary
make test                     # Unit tests with coverage
make testacc                  # Acceptance tests (needs a live Kion + credentials)
make fmt
make lint
make vet
make ci                       # fmt, vet, lint, test — the same checks CI runs
make install                  # Build + copy to ~/.terraform.d/plugins/
make modules-check            # Fail if modules/ is stale
```

Lefthook runs `make ci` as a pre-push hook.

### Testing the generated modules locally

`test:modules` is the CI job most likely to catch a regression, and it is reproducible locally. It builds the provider into a filesystem mirror, regenerates the modules to a scratch directory, then runs `terraform fmt -check`, a drift diff against `modules/`, `terraform validate`, and `terraform test` over every module. See the job in `.gitlab-ci.yml` — running the same steps locally is much faster than discovering a failure in CI.

## CI/CD

### GitLab Pipeline

Runs on merge requests targeting `main`. Stages: `quality`, `test`, `security`, `build`.

| Job | Description |
|-----|-------------|
| `quality:fmt` | `gofmt` formatting check |
| `quality:vet` | `go vet ./...` |
| `quality:lint` | `golangci-lint v2` |
| `test:modules` | Module drift check + `terraform validate` + `terraform test` across all modules |
| `test:unit` | Unit tests with race detection and coverage |
| `sast`, `secret_detection` | GitLab security templates |

The pipeline clones `kion-sdk-go` via CI job token for the `replace` directive.

### GitHub Actions

| Workflow | Trigger | Purpose |
|----------|---------|---------|
| `release.yml` | Tag push (`v*`) | goreleaser → Terraform Registry |

GitLab is the primary pipeline; GitHub carries only the release, because the Registry publishes from a GitHub repo.

## Versioning and Releases

**The provider's version is its own — it does not track Kion's.** Encoding the Kion release in the provider version leaves nowhere to put a provider patch: a fix for the provider against Kion 3.16.4 has no number available, and `~> 3.16` would read as a Kion pin while behaving as a provider pin.

Kion compatibility is a **runtime** mechanism instead. The provider reads `GET /api/version` at configure time and gates each resource against the Kion range its defining API operation exists in (`codegen/version_support.yaml`), failing with a clear diagnostic rather than a confusing API error. The supported window mirrors the SDK's: the current Kion release and three back.

| Change | Bump |
|---|---|
| Provider bug fix | patch — any time, independent of Kion |
| New Kion release adds resources or attributes | minor |
| A provider resource or attribute is removed or renamed | major |

Releases come off `main`; there are no per-Kion release branches. If a released line ever needs a back-patch, branch `release/<provider-major>.x` — keyed to the provider's major, never to a Kion version.

### Changelog

Entries are YAML fragments under `.changes/unreleased/`, one per change, so concurrent merge requests never conflict on `CHANGELOG.md`. `CHANGELOG.md` holds released versions only.

```bash
make changelog-new        # add an entry for your change (interactive)
make changelog-preview    # what the next release notes would say
```

### Cutting a release

```bash
make release-prepare RELEASE_VERSION=1.0.0   # make ci, then batch fragments into CHANGELOG.md
git commit -am "release 1.0.0"
git tag v1.0.0 && git push --follow-tags
```

The tag is the version — nothing in the repo records it. `make version` reports the latest release tag (`0.0.0-dev` on an untagged tree), and that is what `make install` uses for the local plugin path. `make release-snapshot` builds the real artifact set locally without publishing.

The tag triggers `release.yml`, which builds with goreleaser, signs `_SHA256SUMS` with the release GPG key, and attaches the registry manifest — the exact artifact set the Registry requires. Release notes are the changie version file for that tag.

Publishing needs two repository secrets: `GPG_PRIVATE_KEY` (the ASCII-armoured private key) and `PASSPHRASE` (its passphrase), with the matching public key registered on the Registry provider page.

`go.mod` replaces `github.com/kionsoftware/kion-sdk-go` with `../kion-sdk-go`, so nothing compiles without the SDK beside this repo. The release workflow clones it from the SDK's GitHub mirror; set the `SDK_GITHUB_REPO` and `SDK_GITHUB_REF` repository variables to point elsewhere, and pin `SDK_GITHUB_REF` per release so a build is reproducible. That replace also has to go before this repo is public — a clone of it cannot build without the sibling — which needs the SDK published at its module path, `github.com/kionsoftware/kion-sdk-go`.

## Contributing

1. Create a branch from `main`
2. Make changes and ensure `make ci` passes
3. Regenerate any affected generated surfaces (see [Code Generation](#code-generation))
4. Run `make changelog-new` if the change is user-visible
5. Submit a merge request

For new resources, scaffold with `kgen service`, add the `codegen/` entries, and regenerate — do not hand-write CRUD.
